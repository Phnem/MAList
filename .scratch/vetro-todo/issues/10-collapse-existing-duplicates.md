# TICKET-10: Вычистка уже существующих дубликатов в коллекции

## Status

PENDING

## Objective

При проходе по списку коллекции уже возникшие дубликаты схлопываются: из группы остаётся одна запись — более заполненная, дозаполненная тем, что было только у отброшенных.

## User or system value

Вторая половина пункта 9. TICKET-08 закрыл появление **новых** дубликатов, но у пользователя уже накопились записи, созданные прежним поведением (по одной на каждое нажатие).

## Dependencies

**Блокируется TICKET-08** — правило и схлопывание уже реализованы и покрыты тестами там.

## Происхождение тикета

Выделен из TICKET-08 в ходе реализации. Причина (полностью — в Deviations того тикета): `collapseDuplicates` возвращает выжившую запись дозаполненной, и сохранить это одним `deleteAnime(id)` нельзя — нужен путь обновления записи. Операция необратимо удаляет пользовательские данные, поэтому дописывать её без изученного пути сохранения и без проверки на живой БД было нельзя.

Область спеки при этом не изменилась: требование то же, просто вынесено в отдельную единицу работы.

## Scope

- `domain/search/DuplicateTitleRule.kt` — **готово**, менять не требуется. `collapseDuplicates(list)` покрыт 17 тестами.
- Путь сохранения выжившей записи — **предстоит выяснить**. Кандидаты: `SaveAnimeUseCase` с непустым `SaveAnimeParams.animeId`, либо upsert в `AnimeLocalDataSource`.
- Удаление отброшенных: `AnimeLocalDataSource.deleteAnime(id)` (уже используется в `HomeViewModel.deleteAnime`, строки 355–360; там же удаляется файл постера — учесть, чтобы не осиротить или, наоборот, не удалить постер, который вобрала выжившая запись).
- Точка запуска: один раз за сессию, не на каждую эмиссию списка.

## Out of scope

Изменение правила дубликата — оно согласовано и покрыто тестами. Дедупликация при импорте и синхронизации.

## Acceptance criteria

- [ ] При проходе по списку существующие дубликаты схлопываются.
- [ ] Выживает более заполненная запись; избранное/оценка/комментарий не теряются ни при каком порядке записей.
- [ ] Внешние id и переводы, которые были только у отброшенной записи, **сохранены в БД** у выжившей, а не потеряны вместе с ней.
- [ ] Постер выжившей записи не удалён вместе с отброшенной.
- [ ] Схлопывание не запускается на каждую эмиссию списка.
- [ ] Аниме и манга с одинаковым названием обе остаются.
- [ ] Есть тест на путь сохранения, а не только на чистое правило.

## Verification plan

`.\gradlew.bat :app:testDebugUnitTest`, `.\gradlew.bat :app:compileDebugKotlin`.

**Обязательно, прежде чем включать:** проверка на копии реальной БД пользователя, а не только на синтетических данных. Операция необратима.

## TDD classification

REQUIRED — удаление пользовательских данных.

## Expected architecture impact

Появляется путь «прочитать снапшот → схлопнуть → сохранить выжившую → удалить отброшенные». Держать его в одном месте, не размазывая по вызывающим.

## Risks

**Самый высокий в пакете: необратимая потеря пользовательских данных.** Ошибка в пути сохранения (сохранили не всё) или в порядке операций (удалили до сохранения) стоит пользователю прогресса и оценок. Сохранение выжившей записи должно завершиться **до** удаления отброшенных.
