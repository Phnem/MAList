# TICKET-08: Мгновенная кнопка «добавить» и защита от дубликатов

## Status

SUPERSEDED — разделён. Профилактика новых дубликатов сделана здесь; вычистка уже существующих вынесена в **TICKET-10**. Причина разделения — в Deviations.

## Objective

Нажатие «добавить» в поиске сразу переключает кнопку `+add → ✓`, сохранение идёт в фоне, а повторные нажатия и повторные тайтлы не плодят копии. Уже возникшие дубликаты схлопываются при проходе по списку.

## User or system value

Пункт 9 списка. Самый тяжёлый пункт: сейчас это не косметика, а порча данных — пользователь получает по записи на каждое нажатие.

## Dependencies

**Блокируется TICKET-07** (общий файл `ApiSearchResultCard.kt`).

## Scope

- `domain/search/AddFromApiUseCase.kt` — сейчас качает постер и делает detail-запрос к Shikimori **до** сохранения; проверки на дубликат нет вообще, каждый вызов генерирует новый UUID.
- `ui/home/HomeViewModel.kt` — состояние кнопки.
- `ui/home/ApiSearchResultCard.kt` — отображение состояния.

**Обязательные выносы (из архобзора):**

1. Правило дубликата — в чистую функцию, иначе его нечем покрыть тестом.
2. Оптимистичное состояние кнопки — отдельным множеством «добавляется сейчас» во ViewModel. Сейчас кнопка выводится из состояния БД, и это ровно причина отката.
3. `AddFromApiUseCase.invoke` возвращает признак «уже есть», а не голый `Result<Unit>`. Вызывающий один — `HomeViewModel`.

**Правило дубликата** (из `spec.md`, раздел Domain rules): совпадение по внешнему id (`anilistId` / `malId` / `shikimoriId`) при совпадении `mediaType`, **либо** по нормализованному названию при совпадении `mediaType`. Разный `mediaType` дубликатом не является даже при одинаковом названии (аниме и манга с одним названием — разные записи).

**При схлопывании выживает более заполненная запись** (FR-9b): нельзя удалить запись с прогрессом/рейтингом/избранным в пользу пустой.

## Out of scope

Изменение схемы БД. Дедупликация при импорте/синхронизации (Shikimori/AniList/MAL) — отдельная область. Переписывание `SaveAnimeUseCase`.

## Acceptance criteria

- [ ] Кнопка переключается на «✓» немедленно по нажатию, до завершения сохранения.
- [ ] Сохранение продолжается в фоне и доводится до конца.
- [ ] N быстрых нажатий по одной карточке создают ровно **одну** запись.
- [ ] Повторное добавление уже имеющегося тайтла новой записи не создаёт.
- [ ] Аниме и манга с одинаковым названием дубликатом не считаются.
- [ ] При проходе по списку существующие дубликаты схлопываются; выживает более заполненная запись.
- [ ] При ошибке фонового сохранения кнопка откатывается на `+add` и пользователь видит сообщение (молчаливая потеря недопустима — FR-9a).
- [ ] Правило дубликата и схлопывание покрыты unit-тестами: совпадение по id, совпадение по названию, разный `mediaType`, разный регистр/пробелы в названии, выбор более заполненной записи.

## Expected architecture impact

Появляется явный шов правила дубликата с узкой сигнатурой. Оптимистичное состояние перестаёт выводиться из БД. Публичный контракт `AddFromApiUseCase.invoke` расширяется.

## Risks

Схлопывание дубликатов **удаляет пользовательские данные**. Если правило «более заполненная» реализовано неверно, потеряется прогресс. Это самый рискованный тикет пакета — сначала тесты, потом код, и никаких «заодно почищу» в проходе по списку.

## Implementation notes

**Правило дубликата** — `domain/search/DuplicateTitleRule.kt`, чистые функции без зависимостей от Android: `isDuplicate(a, b)`, `collapseDuplicates(list)`, плюс приватные `richness` / `richer` / `absorb`.

Названия сравниваются на **строгое равенство** нормализованных строк (через существующий `normalizeForSearch()`), а не по вхождению. Существующий `isAddedInMemory` использует `contains` — там это допустимо, он лишь красит кнопку, но для удаляющей операции подстрочное сравнение считает «Naruto» и «Naruto Shippuden» одной записью. Закрыто тестом.

**Профилактика новых дубликатов:**

- `AddFromApiUseCase` проверяет дубликат **до** генерации UUID и до скачивания постера, возвращает `AddFromApiOutcome.ALREADY_IN_COLLECTION`. Тип возврата стал `Result<AddFromApiOutcome>` вместо `Result<Unit>`.
- Если тип записи из результата вывести не удалось (`MediaType.fromCategoryType` вернул null), проверка пропускается: правило опирается на `mediaType`, и ошибиться в сторону «добавить лишнее» безопаснее, чем молча отказать.
- `HomeViewModel.addFromApi` отбивает повторное нажатие по тому же ключу (`if (key in optimisticallyAddedKeys) return`). Без этого два вызова успевают пройти проверку до того, как первый допишет запись.

**Оптимистичная кнопка:** `HomeUiState.optimisticallyAddedKeys: PersistentSet<String>`. Состояние выставляется синхронно, до запуска корутины. `isAdded` теперь `key in optimisticKeys || isAddedInMemory(...)` — то есть больше не выводится только из БД, что и было причиной отката. При ошибке ключ снимается и заполняется `apiSearchError`.

## Deviations

- **Планировалось:** один тикет на всё, включая вычистку уже возникших дубликатов.
- **Сделано:** тикет разделён; вычистка вынесена в **TICKET-10**.
- **Причина:** `collapseDuplicates` возвращает выжившую запись *дозаполненной* — вобравшей внешние id и переводы отброшенных. Сохранить это одним `deleteAnime(id)` нельзя, нужен путь обновления записи. Этот путь я не изучал, а операция необратимо удаляет пользовательские данные, и проверить её на живой БД в этой сессии нечем. Дописывать её вслепую противоречит и предупреждению из раздела Risks этого же тикета, и правилу скилла «не помечать сделанным то, что не проверено».
- **Последствия:** сообщённый пользователем баг (кнопка откатывается, N нажатий = N записей) закрыт полностью. Уже существующие в БД дубликаты остаются до TICKET-10.
- **Follow-up:** TICKET-10.

## Review findings

- **TDD соблюдён**: 17 тестов правила написаны до реализации.
- **Проверка стоит в use case, а не в UI** — между нажатием и записью проходит скачивание постера, и проверка в UI гонку не закрывает.
- **Оба защитных механизма нужны**: отбой повторного нажатия во ViewModel закрывает быстрые тапы, проверка в use case — повторное добавление того же тайтла в другой сессии поиска.
- **`ALREADY_IN_COLLECTION` трактуется кнопкой как успех** — галочка правдива, тайтл в коллекции. Откатывать её значило бы предлагать добавить уже добавленное.
- **`RecommendationsViewModel`** тоже вызывает этот use case; смена типа возврата его не сломала (компиляция зелёная), он читает `Result` обобщённо.
- **Не проверено:** поведение на живом устройстве при быстрых повторных нажатиях. Логика покрыта тестами на уровне правила, но не интеграционно.
- Блокирующих замечаний нет.
