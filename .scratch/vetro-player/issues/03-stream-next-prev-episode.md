# TICKET-03: Рабочие кнопки следующей и предыдущей серии в стриминговом плеере

## Status

DONE (реальное переключение с резолвом источника подтверждает пользователь — см. Completion evidence)

## Objective

Кнопки следующей и предыдущей серии в стриминговом плеере переключают серию, резолвя ссылку внутри плеера, без выхода на экран выбора.

## User or system value

Пункт 2 списка.

## Dependencies

**Блокируется TICKET-02** — оба правят `StreamPlayerSurface.kt`.

## Scope

- `media/ui/StreamPlayerSurface.kt` (`:237-238`) — сейчас передаёт `hasPrev = false, hasNext = false` литералами.
- `media/ui/StreamPlayerActivity.kt` — контекст серии (`EXTRA_SEASON`, `EXTRA_EPISODE`, `EXTRA_SEASON_JSON`) читается один раз в `onCreate` и лежит в неизменяемых локальных `val`. Для переключения нужно наблюдаемое состояние текущей серии (находка архобзора).
- Резолв ссылок соседней серии — существующим путём (`StreamWatchViewModel` уже это умеет), за узким интерфейсом «дай ссылки для (season, episode)».

**Решение интервью (D-3):** резолв **внутри плеера**, не возврат к экрану выбора и не предзагрузка.

**Правило из спеки, не нарушать:** «есть соседняя серия по номеру» и «удалось зарезолвить ссылку» — **разные** состояния. Неудачный резолв нельзя показывать как «серии нет».

`PlayerControls` менять не требуется: `hasPrev`/`hasNext` у него уже есть, недоделана только их передача. Интерфейс был спроектирован верно.

## Out of scope

Локальный плеер — там переключение работает через плейлист ExoPlayer, трогать нечего. Предзагрузка соседних серий (отклонена на интервью). Переезд `PlayerControls` в общий пакет (FOLLOW_UP архобзора).

## TDD classification

## Expected architecture impact

Контекст текущей серии стримингового плеера становится наблюдаемым состоянием вместо значений, прочитанных один раз. Появляется узкий интерфейс резолва соседней серии; UI о источниках не знает.

## Risks

- Самый крупный тикет пакета: меняется модель состояния активности, а не только вёрстка.
- Гонка: быстрые нажатия «следующая» подряд могут запустить несколько резолвов. Отбивать так же, как отбивалось повторное добавление в TICKET-08 прогона `vetro-todo`.
- Прогресс просмотра привязан к (`animeId`, `season`, `episode`) — после переключения он обязан писаться для новой серии, иначе просмотр запишется не туда.
- Неизвестное общее число серий не должно превращаться в «серий нет» (правило спеки).

## Implementation notes

Два новых файла в новом пакете `media/episode/`:

**`EpisodeRange.kt`** — чистая арифметика номеров, без Compose и Android. `hasPrevious`, `hasNext`, `previousOf`, `nextOf`. Неизвестное число серий (`null` или `0`) означает «может быть», а не «конец»: иначе неудача резолва выглядела бы как отсутствие серии — прямое нарушение правила спеки.

**`EpisodeStreamResolver.kt`** — узкий интерфейс `suspend resolve(episode, preferredResolution): List<VetroVideo>`, лучший кандидат первым. Плеер знает только номер серии и желаемое разрешение; о хостерах, источниках и о том, как собирается `Anime` для резолва, он не осведомлён. **Пустой список = «ссылку достать не удалось», не «серии нет».**

**Модель состояния активности.** `EXTRA_EPISODE` теперь читается в `initialEpisode`, а внутри `setContent` живёт `var episode by remember { mutableIntStateOf(initialEpisode) }`. От него зависят: заголовок, `episodeNumber` для сегментов автоскипа, поток сохранённого прогресса (`remember(animeId, season, episode)` — иначе `collectAsState` пересоздавал бы подписку на каждой рекомпозиции), периодическая запись прогресса, ключ кэша `VetroVideoCache` и резолв запасных ссылок. Поле `activeEpisode`, которое читает `onStop`, синхронизируется `LaunchedEffect(episode)`.

**`switchToEpisode(target)`** — резолв внутри плеера (D-3): прогресс уходящей серии дописывается ДО подмены (плеер пересоздаётся под новую ссылку, его позиция пропадает вместе с ним), затем резолв, и только по факту успеха меняются `candidates`, `current` и `episode`. До этого момента текущая серия продолжает играть (FR-2a).

`resolveReplacement` (пересборка протухшей ссылки) переписан поверх того же резолвера — дублирующая сборка `Anime` из двух мест ушла в один.

`PlayerControlsOverlay` получил `onPrev`/`onNext` со значением `null` по умолчанию: `null` = прежнее поведение через плейлист ExoPlayer, то есть локальный плеер не изменился ни на строку своего вызова.

FR-3a: `LaunchedEffect(episodeNumber) { zoomState.reset() }` в `StreamPlayerSurface` — поверхность при смене серии не пересоздаётся, поэтому сброс явный.

## Deviations

Отклонений от плана нет. Два решения принято по ходу, оба внутри области тикета:

- **Кнопки гасятся на время резолва** (`switchingTo != null`) — второй заслон от гонки поверх защёлки в самой функции.
- **У сообщения об ошибке переключения есть кнопка «Закрыть»**, а не только «Повторить»: текущая серия продолжает играть, и оверлей не имеет права запирать экран.

## Review findings

- **Гонка отбита в двух местах.** Защёлка `switchingTo` не пускает второй резолв, кнопки на это время неактивны. Отдельно закрыт **второй сценарий гонки, которого в тикете не было**: `refreshStream()` (обновление протухшей ссылки) мог завершиться уже ПОСЛЕ ухода на соседнюю серию и подменить собой ссылку новой серии. Результат теперь сверяется с `refreshingEpisode` и отбрасывается, если серия успела смениться.
- **Прогресс не теряется и не пишется не туда.** Позиция уходящей серии снимается синхронно в момент нажатия (`leavingPosition`/`leavingDuration`) и сохраняется под `leavingEpisode` — не под тем номером, который окажется актуальным к концу резолва.
- **Правило спеки соблюдено:** «есть соседняя серия по номеру» (`EpisodeRange`, чистая функция) и «удалось зарезолвить ссылку» (`EpisodeStreamResolver`, пустой список) — разные состояния и разные типы. Неизвестное число серий оставляет кнопку активной.
- **Новых строк в `UiStrings` нет** — сообщения лежат литералами рядом с уже существующими литералами этого экрана («Обновляем ссылку на поток…», «Повторить»).
- **`layerBackdrop` не задет**, модификаторы структурно не добавлялись.
- **Локальный плеер:** `PlayerScreen.kt` не изменён; новые параметры `PlayerControlsOverlay` имеют дефолты, ветка `player.seekToNextMediaItem()` сохранена.
- Блокирующих замечаний нет.
