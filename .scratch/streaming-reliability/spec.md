# Надёжное потоковое воспроизведение

## Problem

На нестабильном зеркале скорость отдельных загрузок может падать до 200–400 кбит/с. Буфер
исчерпывается, а плеер остаётся в `BUFFERING` на 10–20 минут, потому что медленная передача не
является socket timeout и текущая автоматика реагирует только на окончательную ошибку.

## Desired outcome

Потоковый плеер должен заранее накапливать безопасный буфер, консервативно выбирать качество,
отменять заведомо неуспевающий adaptive-чанк и автоматически уходить на более безопасное качество
или другое зеркало, не теряя позицию. Причины решения должны быть видны в обезличенной телеметрии.

## Current behavior

- Фабрика streaming session уже содержала незакоммиченную настройку увеличенного буфера и
  базовый `AnalyticsListener`.
- Media3 зафиксирован на `1.4.1`; streaming-only setters из более новой release-ветки отсутствуют.
- Локальный и потоковый плееры создаются разными фабриками, поэтому общий setter внутри
  remote-player factory фактически затрагивает только streaming.
- Большинство источников публикуют независимые URL для 480/720/1080 или зеркал. Настоящий
  multi-variant manifest тоже поддерживается, но не гарантирован.
- Пересоздание/смена URL выполняется только после `PlayerError`; медленная бесконечная загрузка
  ошибкой не становится. Максимум автоматических повторов равен восьми.

## Required behavior

1. Каждая media/manifest-загрузка получает коррелируемую, безопасную для логов телеметрию:
   `loadId`, host, response code (когда доступен), качество, declared bitrate, segment duration,
   expected/actual bytes, request start, TTFB, rolling 1s/3s throughput, no-progress interval,
   buffer at start/end, cancellation reason и selected source.
2. Отдельно логируются `allocator.totalBytesAllocated`, configured target-buffer mode, `isLoading`
   и buffered duration. URL, query, headers, токены и тексты сетевых исключений не логируются.
3. Только потоковый плеер использует buffer 60/90 секунд, старт после 2 секунд, возобновление после
   rebuffer после 6 секунд и приоритет временного порога над byte target.
4. Для настоящего adaptive track group: повышение качества не раньше 25 секунд, снижение при
   10 секундах, bandwidth fraction 0.60, discard обычных 360–720p чанков ради повышения выключен.
5. Если adaptive-чанк находится не дальше 10 секунд от позиции, существует более низкий трек и
   4 секунды нет прогресса либо прогноз загрузки не помещается в безопасный буфер, загрузка
   отменяется. Повторная отмена того же сегмента запрещена 15 секунд; текущий и более высокие
   треки исключаются на 25 секунд.
6. Для независимых URL watchdog не ждёт сетевой ошибки: после 8 секунд непрерывного `BUFFERING`
   он инициирует восстановление. Позиция сохраняется, текущий URL помечается плохим на сессию,
   затем выбирается другой host с не более высоким качеством, более низкое качество на том же
   host, иной host или выполняется повторный resolve.
7. Retry зависит от буфера: при >20 сек допустима одна пересборка того же URL; при 8–20 сек — одна
   быстрая пересборка; при <8 сек повтор того же URL запрещён и нужен fallback/resolve.
8. HTTP 403 направляет в повторный resolve, 404/410 — в fallback/resolve, 429/503 при буфере <8 сек
   — в fallback, а при безопасном буфере допускает единственный локальный retry.

## User-visible behavior

- Долгий spinner сам завершается попыткой резервного источника примерно через 8 секунд.
- При восстановлении сохраняется текущая позиция и уже существующий loading indicator.
- Ручное переключение качества/озвучки и воспроизведение скачанных серий не меняются.

## Domain rules

- `VetroVideo` — одна готовая к проигрыванию rendition; соседние `VetroVideo` не считаются
  синхронизированными adaptive-вариантами.
- Adaptive cancellation применяется только внутри track group, созданного Media3 из одного
  manifest. Между `VetroVideo` переключается координатор на уровне сессии.
- «Неизвестный размер» остаётся неизвестным; bitrate × duration используется только как последний
  приблизительный источник и не должен маскироваться под точный размер.

## Functional requirements

- Восстановление не должно циклически возвращаться к уже провалившемуся URL в той же сессии.
- Одновременно выполняется не более одного recovery action.
- Устаревший результат resolve для другой серии игнорируется.
- На успешном `READY` счётчик локальных повторов сбрасывается, но плохие URL текущей сессии — нет.

## Non-functional requirements

- Решения policy и выбор кандидата покрываются детерминированными unit-тестами.
- Горячий callback `onBytesTransferred` не пишет лог на каждый пакет и хранит ограниченную историю.
- Публичная поверхность streaming-модуля остаётся малой: одна фабрика сессии и снимок прогресса.

## Compatibility and migration constraints

- Media3 остаётся `1.4.1` в этом пакете: upgrade не нужен для результата и несёт отдельный риск.
- Используются доступные в `1.4.1` `setBufferDurationsMs` и
  `setPrioritizeTimeOverSizeThresholds`; они находятся в фабрике только потокового плеера.
- Формат сериализации `VetroVideo` не ломается.

## Failure and fallback behavior

- Если готового кандидата нет, координатор повторно резолвит серию, исключая все уже виденные URL.
- Если resolve ничего не вернул, показывается существующая ошибка с ручным `Повторить`.
- Recovery не сбрасывает пользовательскую позицию и не меняет номер серии.

## Out of scope

- Level 2/3 из исходного плана: постоянный host-health store, отдельный long-term estimator,
  NORMAL/DANGER/PANIC/RECOVERY автомат, MPC и ML-ABR.
- Проверка реальной CDN-пропускной способности без устройства/тестового стенда.
- Обновление Media3 и DASH regression #3326.

## Acceptance criteria

- [ ] Unit-тесты доказывают rolling throughput, TTFB/no-progress и cooldown отмены.
- [ ] Логи завершённой/отменённой загрузки содержат перечисленные поля и не содержат URL/секреты.
- [ ] Streaming-конфигурация соответствует 60/90/2/6, 25/10/25, 0×0, 0.60.
- [ ] Локальная фабрика проигрывания не изменена.
- [ ] Unit-тесты доказывают buffer-aware retry и порядок fallback-кандидатов.
- [ ] Watchdog инициирует ровно одно восстановление после 8 секунд `BUFFERING`.
- [ ] Позиция переносится при watchdog/error recovery.
- [ ] Targeted unit tests, `compileDebugKotlin` и `assembleDebug` проходят либо известные исходные
  падения явно отделены.
- [ ] На устройстве подтверждены: stall не длится 10–20 минут, позиция сохраняется, нет цикла.

## Open questions

- `DEFERRED`: фактическая доля multi-variant manifest станет известна из телеметрии track count;
  это влияет только на ценность adaptive cancellation, не блокирует реализацию.
- `SAFE_DEFAULT`: не обновлять Media3; безопасно из-за раздельной streaming-фабрики и доступности
  нужных базовых интерфейсов в 1.4.1. Позже меняется отдельным dependency ticket.
- `DEFERRED`: точные пороги корректируются только после полевых метрик, не «на глаз».

## Test seams

- Чистый accumulator transfer-прогресса с инъекцией monotonic time.
- Чистая recovery policy.
- Чистый ranking fallback-кандидатов.
- Stall-aware track selection через синтетические snapshot/chunk inputs где Media3 допускает.
