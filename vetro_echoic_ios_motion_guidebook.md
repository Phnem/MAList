# Vetro Echoic — iOS Motion & Materials: полный гайдбук
### Справочник для AI-агента (Kotlin / Jetpack Compose)

Собран из трёх источников: изначального справочника этого чата, и двух PDF
(`Vetro_Echoic_-_iOS_Motion_Materials_Design_Recipes` и `UI_Гайдлайны_Анимации_и_Визуалы`).
Там, где источники расходились в цифрах — расхождение разобрано явно (см. пометки
**⚠ расхождение источников**), а не спрятано под одной случайно выбранной цифрой.
Там, где в одном из PDF была математическая ошибка — она исправлена, со сноской.

**Важная оговорка о точности чисел.** Формула конвертации пружины (раздел 2.1) —
аналитически точна и выводится напрямую из документированного Apple API. Остальные
числа (padding, elevation, пороги свайпов, конкретные alpha) — это откалиброванные
практические рекомендации на основе публичных HIG-гайдлайнов и многолетней
реверс-инженерии сообществом, а не выгруженные из закрытого исходного кода Apple
константы. Это рабочие дефолты, которые дают достоверный "iOS-фидбэк" — тюнинг на
глаз по месту приветствуется.

## Как этим пользоваться
Положи файл в репозиторий (`docs/ios_motion_guidebook.md`) и сошлись на него в
инструкциях агента: **Claude Code** — в `CLAUDE.md` ("сверяйся с

## 2. Общая математика движения

### 2.1 Аналитическая конвертация пружины: SwiftUI → Compose

SwiftUI параметризует пружину через `response` (время отклика, сек) и
`dampingFraction` (0..1). Compose — через `stiffness` и `dampingRatio`. При массе
объекта `mass = 1.0` (дефолт Compose) конвертация точна:

```
ωn = 2π / response                  // собственная угловая частота
stiffness   = ωn²  =  (2π / response)²
dampingRatio = dampingFraction      // это буквально одна и та же величина
```

Это прямое следствие уравнения затухающего гармонического осциллятора и совпадает
с тем, как параметризована сама SwiftUI Spring API — не приближение, а точный пересчёт
при mass=1.

**Проверочная таблица** (расчёт по формуле выше, использовалась для калибровки всех
токенов ниже):

| Паттерн | SwiftUI response | SwiftUI damping | Compose stiffness | Compose dampingRatio |
|---|---|---|---|---|
| Медленное величественное появление | 0.65 | 0.86 | ≈93.5 | 0.86 |
| Стандартный интерактивный (дефолт iOS) | 0.55 | 0.825 | ≈130.5 | 0.825 |
| Быстрый menu pop | 0.35 | 0.65 | ≈322.0 | 0.65 |
| Hero-переход (карточка→окно) | 0.50 | 0.70 | ≈157.9 | 0.70 |
| Нажатие кнопки | 0.20 | 0.60 | ≈986.9 | 0.60 |

### 2.2 Каноническая таблица токенов

Часть токенов выведена аналитически (2.1), часть — это практические значения,
специфичные для конкретных Compose-паттернов (bottom sheet, overscroll и т.д.), для
которых у Apple нет опубликованного response/damping — тут все источники (включая
оба PDF) независимо сошлись на практике, а не на теории.

| Токен | stiffness | dampingRatio | Тип | Применение |
|---|---|---|---|---|
| `motion.standard` | 130.5 | 0.825 | аналитический | дефолт, если нет более специфичного токена |
| `motion.modalSlow` | 93.5 | 0.86 | аналитический | крупные величественные раскрытия (альтернатива для сценария 1) |
| `motion.heroCard` | 157.9 | 0.70 | аналитический | карточка → полноэкранное окно (сценарий 6) |
| `motion.menuPop` | 500 | 0.62 | практический (3/3 источника сошлись) | выпадающие/контекстные меню, лёгкий перелёт |
| `motion.press` | 987 | 0.60 | аналитический | нажатие кнопки/строки |
| `motion.sheetPresent` | 380 | 0.86 | практический | появление bottom sheet, дока-окна |
| `motion.sheetDismissForced` | 700 | 1.0 | практический, критическое затухание | принудительный дисмисс после fling — без отскока |
| `motion.overscrollReturn` | 400 | 1.0 | практический, критическое затухание | возврат "резинки" после оверскролла |
| `motion.barReveal` | 500 | 0.9 | практический | быстрый возврат бара при скролле вверх |
| `motion.dialogPop` | 500 | 0.75 | практический | попап-диалог (сценарий 7) |

```kotlin
object MotionTokens {
    val standard = spring<Float>(dampingRatio = 0.825f, stiffness = 130.5f)
    val modalSlow = spring<Float>(dampingRatio = 0.86f, stiffness = 93.5f)
    val heroCard = spring<Float>(dampingRatio = 0.70f, stiffness = 157.9f)
    val menuPop = spring<Float>(dampingRatio = 0.62f, stiffness = 500f)
    val press = spring<Float>(dampingRatio = 0.60f, stiffness = 987f)
    val sheetPresent = spring<Float>(dampingRatio = 0.86f, stiffness = 380f)
    val sheetDismissForced = spring<Float>(dampingRatio = 1.0f, stiffness = 700f)
    val overscrollReturn = spring<Float>(dampingRatio = 1.0f, stiffness = 400f)
    val barReveal = spring<Float>(dampingRatio = 0.9f, stiffness = 500f)
    val dialogPop = spring<Float>(dampingRatio = 0.75f, stiffness = 500f)
}
```

### 2.3 Время устаканивания (settle time)
`t_settle ≈ 4.6 / (dampingRatio · ωn)`, где `ωn = sqrt(stiffness / mass)`. Полезно, когда
нужно запустить вторую анимацию в цепочке (сценарий 2, 6) — не гадать на глаз, а
дождаться реального завершения первой.

### 2.4 Rubber band (оверскролл) — исправленная формула
⚠ **Расхождение источников.** В одном из PDF («Vetro Echoic Design Recipes», раздел 8)
приведена формула `delta = dragAmount * (1f - (currentOverscroll / maxOverscroll))` —
это **математически неверно**: линейное затухание, а не асимптотическое, и оно
достигает нуля при конечном `x`, что не соответствует реальному эффекту (контент
"упирается в стену" вместо бесконечно убывающего сопротивления). Верная формула
(подтверждена независимо: реверс-инжиниринг `UIScrollView`, воспроизведена в обоих
источниках одинаково и совпадает с моим собственным поиском):

```
b(x, d, c) = (1 − 1 / (x·c/d + 1)) · d   ≡   (x · d · c) / (d + c·x)
```
- `x` — дистанция протяжки за границу
- `d` — размер вьюпорта (высота/ширина), к которому асимптотически стремится эффект
- `c = 0.55` — константа Apple

Пример (d=960px, c=0.55): x=100 → b≈52px; x=400 → b≈179px; x=960 → b≈341px. Значение
никогда не достигает `d` — контент физически не может "оторваться" больше, чем на
размер экрана. При отпускании — `motion.overscrollReturn` (критическое затухание, без
отскока).

### 2.5 Инерция и торможение (fling deceleration)
Скорость после отпускания пальца затухает экспоненциально:
```
v(t) = v0 · δ^t
x(t) = x0 + v0·(δ^t − 1) / ln(δ)
X_final = x0 − v0 / ln(δ)                 // точка, где список остановится
```
`δ` — `decelerationRate`. Apple использует две константы:
`UIScrollViewDecelerationRateNormal = 0.998`, `...Fast = 0.990` (доля скорости,
сохраняющаяся за миллисекунду). В Compose это не нужно реализовывать руками —
есть готовые `rememberSplineBasedDecay()` / `exponentialDecay()` в
`androidx.compose.animation.core`; калибруй под 0.998 для обычного скролла.

### 2.6 Матчинг геометрии (dock/карточка/кнопка → окно)
Аналог Apple `matchedTransitionSource` + `.navigationTransition(.zoom)` (iOS 18+). В
Compose — `SharedTransitionLayout` + `Modifier.sharedElement`/`sharedBounds`.

```
x(t) = lerp(x0, x1, t);  y(t) = lerp(y0, y1, t)
w(t) = lerp(w0, w1, t);  h(t) = lerp(h0, h1, t)
```

**Важный нюанс по радиусу**, которого нет ни в одном из PDF: если источник —
squircle-иконка (не капсула), обычный `lerp(r0, r1, t)` работает нормально (см.
сценарий 1). Но если источник — **капсула** (r = height/2, например кнопка в
сценарии 4), голый lerp по абсолютному радиусу на середине пути даёт неправильную
форму. Тогда интерполируй радиус как **долю** от `min(w,h)/2`:
```
rFraction(t) = lerp(r0 / (min(w0,h0)/2), r1 / (min(w1,h1)/2), t)
r(t) = rFraction(t) * min(w(t), h(t)) / 2
```
Контент масштабируется как `s(t) = w(t) / w0`; кросс-фейд между компактным и
развёрнутым содержимым — в окне `progress ∈ [0.3, 0.7]`.

**Правило соотношения сторон** (важно для сценария 6): чистый geometric zoom хорошо
смотрится, только если источник и назначение похожи по aspect ratio.
```
aspectRatioDelta = max(wSrc/hSrc, hSrc/wSrc) / max(wDst/hDst, hDst/wDst)
if aspectRatioDelta > 1.5..2.0 → используй content cross-fade вместо чистого zoom
else → геометрический матчинг как есть
```

### 2.7 Порог fling/дисмисса
```
willDismiss = (offset > 0.5 * containerSize) OR (abs(velocity) > vThreshold)
```
⚠ **Расхождение источников**: один PDF даёт `vThreshold = 500dp/с`, другой (и мой
исходный вариант) — `1200dp/с`. У Apple нет опубликованного точного числа для
кастомных sheet-жестов — оба значения тюнинговые. Практическая рекомендация:
начни с **~800dp/с** и подстрой на ощупь; 500 может закрывать шторку слишком охотно
при обычном скролле контента внутри, 1200 может ощущаться "тугим".

## 3. Дизайн-токены

### 3.1 Радиусы
| Токен | Значение | Где |
|---|---|---|
| `radius.xs` | 8dp | чипы, микро-контролы, внутренние элементы списков |
| `radius.sm` | 12–14dp | кнопки, иконки дока |
| `radius.md` | 16–20dp | карточки, диалоги, контекстные меню |
| `radius.lg` | 24–28dp | bottom sheet, док-панели, полноэкранные карточки |

Всегда через `squircle-shape` (continuous curvature, smoothing 0.6–0.7), не голый
`RoundedCornerShape`.

### 3.2 Материалы — двухуровневая система
Прямое следствие того, к чему сама Apple откатилась в iOS 27 после жалоб на
нечитаемость избыточной прозрачности.

**Уровень 1 — настоящее стекло** (`Kyant0.backdrop`: blur + lens + vibrancy). Дорого,
использовать точечно: доки, floating tab bar, контекстные меню, выпадающие меню.

| Токен | Блюр | Где |
|---|---|---|
| `glass.thin` | лёгкий | tab bar, тонкие плавающие панели |
| `glass.regular` | средний + vibrancy | **дефолт для доков и выпадающих меню** |
| `glass.thick` | сильный | модалки поверх насыщенного контента |

**Уровень 2 — дешёвая alpha-поверхность** (без рефракции). Везде, где стекло не несёт
смысловой нагрузки: диалоги, обычные карточки, списки.
```
Color.White.copy(alpha = 0.85f)   // light theme
Color.Black.copy(alpha = 0.75f)   // dark theme
```
Можно дополнить сверхлёгким `Modifier.blur(10.dp)` без рефракции — не более того.

`scrim.default` — чёрный, alpha **0.30–0.45**, fade всегда синхронно со входом
контента (не до и не после).

### 3.3 Цвета для сгруппированных списков (iOS system palette)
| Токен | Light | Dark |
|---|---|---|
| фон экрана за списком | `#F2F2F7` | `#000000` |
| фон карточки/строки | `#FFFFFF` | `#1C1C1E` |
| разделитель | `#C6C6C8` | аналог с приглушённой яркостью |
| chevron / вторичные иконки | `#C7C7CC` | аналог |
| highlight при нажатии строки | `#D1D1D6` (light) | тональный аналог |

Маппи эти значения в семантические токены `MaterialTheme.colorScheme`, а не хардкодь
hex — так тема будет адаптивной.

**Платформенная поправка (Android-специфика, которой нет ни в одном источнике-PDF):**
iOS-разделитель — `0.5pt` (= 1 физический пиксель на Retina). На Android при разной
плотности экрана суб-1dp линии рендерятся непредсказуемо (то видны, то нет). Практическая
рекомендация — **`1.dp`** сплошной линии с alpha ~0.15–0.2 вместо попытки буквально
попасть в 0.5dp.

## 4. Сценарий 1 — [Анимация] Новое окно из дока

**Механизм** — геометрический матчинг (2.6), НЕ scale+fade. Иконка "раскрывается" в
окно через shape morphing.

| Параметр | Значение |
|---|---|
| источник | иконка дока, squircle, `radius.sm` (12–14dp) |
| назначение | почти full-screen окно, `radius.lg` (24–28dp) верхние углы (0, если edge-to-edge) |
| материал источника | `glass.regular`, пока это компактная иконка |
| материал назначения | **сплошная поверхность** (не блюр!) — рендерить полноэкранный блюр во время быстрой транзишена нецелесообразно по перформансу |
| фон позади (rest of app) | `scale 1→0.95`, затемнение `alpha 0→0.3` |
| пружина | `motion.sheetPresent` (380/0.86) для отзывчивого фидбека, либо `motion.modalSlow` (93.5/0.86) для более "величественного" раскрытия — выбор стилистический |

Радиус — обычный `lerp(r0, r1, progress)` (иконка не капсула, фракционная формула
из 2.6 тут не обязательна). Контент внутри окна — `alpha 0→1` в первые ~30% анимации,
чтобы не показывать сжатый текст.

**Interactive Highlight** (деталь Liquid Glass): во время трансформации по поверхности
двигается радиальный градиент с низким alpha, эмулируя блик проходящего света —
подключай `progress` как источник его позиции.

```kotlin
SharedTransitionLayout {
    AnimatedContent(targetState = isWindowOpen, label = "dockWindow") { open ->
        if (!open) {
            DockIcon(
                modifier = Modifier.sharedBounds(
                    rememberSharedContentState(key = "window"),
                    animatedVisibilityScope = this@AnimatedContent
                )
            )
        } else {
            FullScreenWindow(
                modifier = Modifier.sharedBounds(
                    rememberSharedContentState(key = "window"),
                    animatedVisibilityScope = this@AnimatedContent,
                    boundsTransform = { _, _ -> MotionTokens.sheetPresent }
                )
            )
        }
    }
}
```

## 5. Сценарий 2 — [Анимация] Dropdown-меню из верхнего дока + переход в окно

Два движения подряд — не одна анимация.

**5.1 Появление dropdown**
- `transformOrigin` = точка анкора (кнопка/элемент дока, который открыл меню) — НЕ
  геометрический центр экрана
- `scale: 0.85 → 1.0`, `motion.menuPop` (500/0.62 — лёгкий перелёт)
- `alpha: 0 → 1`, `tween(120)` — короче scale, чтобы контент проявлялся уже почти в
  финальной форме
- материал: `glass.regular` — это дефолт для выпадающих меню по собственной же
  таблице токенов (3.2); не `glass.thick` — более тяжёлый материал тут избыточен
- тень для оптического отрыва от контента: `elevation 16dp`, `ambientColor = Black(0.1)`,
  `spotColor = Black(0.15)`, смещена вниз по Y
- пункты списка проявляются каскадом: `delay = index * 30ms`, EaseOut — не все сразу

**5.2 Переход: выбранный пункт → окно**
- Источник геометрического матчинга (2.6) — rect конкретной выбранной строки, НЕ
  всего dropdown целиком
- Остальные строки: `alpha 1→0`, `scale 1→0.95`, `tween(100..150)`, стартует до zoom
- Дождись `t_settle` (2.3) первой анимации (~100–150ms) перед стартом zoom — иначе
  два движения "дерутся" визуально
- Дальше — тот же матчинг, что в сценарии 1, `radius.md → radius.lg`

## 7. Сценарий 4 — [Анимация] Bottom menu из элемента (кнопки)

Отличие от "просто bottom sheet" — меню должно визуально вырасти ИЗ кнопки, а не
выехать с нижнего края. Это геометрический матчинг (2.6) с капсулой-источником —
здесь фракционная формула радиуса обязательна.

| Параметр | Значение |
|---|---|
| триггер | кнопка проседает `scale → 0.96` на нажатие, токен `motion.press` |
| источник матчинга | frame кнопки (капсула, `r = height/2`) |
| назначение | frame шторки (ширина экрана − отступы, высота = контент) |
| появление | `motion.sheetPresent` (380/0.86) |
| scrim | заливка всего фона (Tween 250ms); технически исключить саму кнопку из scrim сложно — либо overlay-трюк, либо просто заливать весь фон |

Углы морфятся асимметрично (см. формулу в 2.6):
```
topLeft(t)     = lerp(rButton, radius.lg, t)
topRight(t)    = lerp(rButton, radius.lg, t)
bottomLeft(t)  = lerp(rButton, 0f, t)
bottomRight(t) = lerp(rButton, 0f, t)
```

**Drag-to-dismiss:**
```
offsetY_current = max(0, offsetY_previous + dragAmount)   // 1:1 с пальцем
willDismiss = (offsetY > 150dp) OR (velocity_down > ~800dp/s)   // см. 2.7 про разброс порога
```
При дисмиссе — `motion.sheetDismissForced` (700/1.0, критическое затухание, без
отскока внизу). При слабом жесте — пружина возврата `motion.sheetPresent`.

Начальный офсет шторки задавай не магическим числом (`+1000dp`), а фактической
высотой контейнера, посчитанной через `onGloballyPositioned` — иначе на высоких
экранах/планшетах шторка может стартовать уже частично видимой.

## 8. Сценарий 5 — [Визуал] Список элементов (например настройки)

Классический Inset Grouped List.

| Параметр | Значение |
|---|---|
| высота строки | мин. 44dp, обычно 48–56dp с иконкой |
| leading icon | 28–30dp squircle, скругление 6–8dp, цветная заливка своя на функцию (как Settings.app), белая иконка 16–18dp внутри |
| insets | 16dp слева/справа |
| divider | `1.dp` (Android-поправка из 3.3), inset = сумма левых элементов: `16 + 28 + 12 = 56dp` от левого края — линия никогда не касается края экрана |

| фон | см. таблицу 3.3 |

⚠ **Важно, легко упустить, портируя с Material Design:** здесь категорически

fade-out. Если используешь стандартный Compose `Indication` — переопредели его
кастомной реализацией, а не полагайся на дефолтный ripple темы.

## 9. Сценарий 6 — [Анимация] Открытие/закрытие окна из карточки (Hero animation)

Тот же механизм геометрического матчинга (2.6), что в сценарии 1, но с тремя
синхронными процессами вместо одного:

1. **Морфинг карточки**: пример — источник 300×400dp, `radius.md` (16dp) → экран
   `Wscreen×Hscreen`, радиус → 0 (или `radius.lg` на верхних углах, если не полностью
   edge-to-edge)
2. **Реакция фона**: список позади уменьшается `scale 1.0→0.92`, скругление углов
   списка (если он занимал весь экран) увеличивается — имитация удаления вглубь Z
3. **Подъём по Z**: карточка отбрасывает растущую размытую тень, которая исчезает,
   когда карточка полностью перекрывает экран

Пружина — `motion.heroCard` (157.9/0.70, аналитически из response=0.5/damping=0.7) —
намеренно более "затяжная", чем sheet-токены, чтобы мозг успел обработать
пространственный переход.

**Правило соотношения сторон** (2.6): если источник узкий/длинный (как строка
списка), чистый zoom "мнёт" контент — используй cross-fade вместо геометрии.

**Контент внутри** не тупо масштабируется, а перестраивается под целевой размер:
текстовые узлы позиционируются через `Alignment.TopStart` с интерполяцией отступов,
и получают собственный `alpha`-переход, а не наследуют масштаб контейнера один в
один — иначе текст визуально "плывёт"/пикселизуется в середине анимации.

**Закрытие** — интерактивный жест (свайп вниз), `t` матчинга управляется напрямую
смещением пальца, а не таймером. Под сильным натяжением карточка может
дополнительно уменьшаться (`scale ~0.85`) — тактильный намёк на "уже почти закрыто".
При отпускании — порог из 2.7 решает: доанимировать до конца или спружинить обратно.

## 10. Сценарий 7 — [Визуал]+[Анимация] Попап-диалог

В отличие от сценариев 1/4/6, диалог **не вырастает** из источника — отдельный
модальный слой без геометрического матчинга. Также отличается от сценария 3
(информационное окно) наличием ударной входной физики — это разные кейсы, не
путать.

| Параметр | Значение |
|---|---|
| позиция | центр экрана |
| ширина | 270–300dp на телефоне, до ~560dp на планшете |
| padding | 20dp внутренний |
| высота тап-зоны кнопок | 44dp |
| скругление | `radius.md`, squircle |
| материал | Уровень 2 — читаемость важнее эффекта стекла (опционально vibrancy для смешивания текста с фоном, как в нативных iOS-алертах) |
| scrim | чёрный alpha 0.4, **строго синхронно** со входом диалога, ровно `tween(250)` |

**Входная анимация** — ⚠ источники разошлись в направлении масштаба: один вариант
предлагает рост "снизу" (0.9→1.0), другие два (независимо) — "усадку сверху"
(1.15–1.2→1.0), имитируя физическое "приземление" объекта. Логика источников с
усадкой сильнее и подтверждена дважды — берём её как основную:
```
scale: 1.15 → 1.0
alpha: 0.0 → 1.0, tween(200)
spring: motion.dialogPop (500/0.75)
```
Опциональный микро-эффект (лёгкий undershoot до ~0.98 перед стабилизацией на 1.0)
достижим при чуть более низком dampingRatio (~0.65–0.7) — необязательно, но
"тактильно" ощущается как физический вес объекта.

**Выход:** `scale → 0.9`, `alpha → 0.0`, `tween(150)` — диалог "проваливается" назад,
без пружины (обычный tween, чтобы закрытие ощущалось быстрее открытия).

**Кнопки:** 2 кнопки — горизонтальный ряд; 3+ — вертикальный список с разделителями;
деструктивное действие — красный текст, обычное — акцентный цвет.

## 11. Сценарий 8 — [Анимация] Скролл: оверскролл, scroll edge effect, скрытие баров

Три независимые механики.

### 11.1 Оверскролл / rubber band
Формула — 2.4 (исправленная). Для компонента (не всего экрана) бери `d` меньше
высоты вьюпорта (150–200dp) — эффект ощущается "тугим", без нужды тянуть на
полэкрана. Возврат — `motion.overscrollReturn` (400/1.0, критическое затухание, без
колебаний).

**Реализация в Compose** — с версии Compose Foundation 1.8.0 доступен интерфейс
`OverscrollEffect` для низкоуровневой настройки (сверься с актуальной версией в
проекте, API молодое и может отличаться):
- `applyToScroll` — накапливает виртуальную дельту `x` при протяжке за границу,
  применяет формулу 2.4 с `c=0.55`, конвертирует в графическое `Modifier.offset`
- `applyToFling` — если "резинка" натянута (offset ≠ 0), запускает `motion.overscrollReturn`
  вместо обычной инерции

### 11.2 Инерция (fling)
Формулы — 2.5. Готовые Compose-примитивы: `rememberSplineBasedDecay()` /
`exponentialDecay()` из `androidx.compose.animation.core`, калибровка под δ≈0.998.

### 11.3 Scroll edge effect (материал бара реагирует на контент под ним)
Паттерн из iOS 26 (`scrollEdgeEffectStyle`/`UIScrollEdgeElementContainerInteraction`,
поддерживает `.soft`/`.hard` per-edge стили). Пока список в самом верху
(`offset = 0`) — бар над ним полностью прозрачен (`alpha=0, blur=0`), сливается с
фоном. Как только контент заезжает под бар (`offset > 0`) — материал
материализуется: непрозрачность и радиус блюра линейно интерполируются от 0 до
целевого значения в диапазоне `offset ∈ [0, 40..50dp]`.

Реализация: `NestedScrollConnection` трекает `scrollOffset`, нормализует
`[0, 50dp] → [0.0, 1.0]`, используй как множитель альфа-канала для слоя бара (или
как alpha-маску поверх `Modifier.blur()`, через `graphicsLayer` + `BlendMode.DstIn`).

### 11.4 Скрытие/схлопывание плавающих баров
Асимметричный порог — важная деталь, отсутствующая в PDF-источниках, но
соответствующая реальному поведению Apple (`tabBarMinimizeBehavior`): схлопывание
при скролле вниз требует порога (**~60dp** непрерывного скролла), а разворот при
скролле вверх — почти мгновенный (1–2dp достаточно). Реализация — тот же
`NestedScrollConnection`, копящий `collapseFraction: Animatable<Float>` через
`snapTo` во время активного драга и `animateTo(motion.barReveal)` при остановке.
НЕ трогай `collapseFraction` на программном скролле (`scrollToItem`) — только на
пользовательском drag.

## 12. Бонус — Контекстное меню (long-press)

Это **девятый**, отдельный паттерн — не путать со сценарием 7 (попап-диалог). В
одном из PDF он был ошибочно подписан как "попап диалог", хотя по содержанию
описывает именно long-press context menu — здесь это исправлено и вынесено отдельно.

- Долгое нажатие → source view "проваливается": `scale → 0.95–0.96` за 150–200ms
- Поверх всей иерархии — оверлей `glass.regular`/`glass.thick` (в зависимости от
  насыщенности фона) + затемнение `alpha 0.1–0.2`
- Меню появляется у источника (сверху/снизу — по доступному месту), `radius.md`,
  вылетает из точки привязки: `scale 0.2 → 1.0`, `motion.menuPop` (500/0.62 —
  перелёт, меню слегка "перерастает" размер перед стабилизацией)
- Глубокая рассеянная тень для оптического отрыва от размытого фона
- Compose: системный `Popup` с отключённым клиппингом + кастомный
  `PopupPositionProvider`; исходный элемент дублируется в overlay (`graphicsLayer`
  либо программный снимок), чтобы отрисовываться поверх затемнённого/размытого фона
